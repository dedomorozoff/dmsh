# План реализации — Улучшения nlsh

Мы предлагаем набор улучшений, чтобы сделать `nlsh` (Natural Language Shell) более стабильным, настраиваемым и удобным для пользователя. Эти улучшения затрагивают конфигурацию, удобство работы с REPL, безопасность и устойчивость модели.

## Предлагаемые улучшения

### 1. Интерактивный CLI для конфигурации (`nlsh config`)
Добавление новой группы команд `nlsh config`, которая позволит пользователям управлять настройками прямо из терминала вместо ручного редактирования `config.json`:
* `nlsh config show`: вывод текущей конфигурации (ключи, значения и указание, дефолтные они или переопределенные).
* `nlsh config set <key> <value>`: валидация ключа и установка нового значения с сохранением в `~/.config/nlsh/config.json`.
* Поддержка основных параметров: `model`, `threads`, `ctx_size`, `gpu_layers`, `temperature`, `top_p`, `shell`, `dry_run`, `mode`.

### 2. Автодополнение файлов и директорий в REPL
Сейчас автодополнение по `Tab` работает только для команд, начинающихся со слэша (slash commands). Мы реализуем умное автодополнение путей:
* Когда пользователь вводит `/cd ` или `/cd <префикс>`, будет автодополняться имя поддиректории из текущей рабочей папки.
* При вводе обычных команд по нажатию Tab будут дополняться имена файлов и папок на основе текущего пути.

### 3. Полноценный просмотр истории (`/history` и `nlsh history`)
Сделаем так, чтобы команда просмотра истории действительно читала сохраненные данные из `history.jsonl` вместо вывода заглушки:
* `/history` в REPL будет читать последние 20 записей из `~/.config/nlsh/history.jsonl` (объединяя историю текущей сессии и прошлых запусков).
* Добавим команду `nlsh history` в CLI для отображения и поиска (grep) по выполненным ранее командам.

### 4. Пользовательские правила безопасности в конфиге
Позволим пользователям расширять правила безопасности без изменения исходного кода.
* Добавим массивы `danger_patterns` и `suspicious_patterns` в структуру `config.Config`.
* Эти регулярные выражения будут компилироваться при запуске и оцениваться вместе со стандартными правилами в `internal/policy`.

### 5. Устойчивый резервный JSON-парсер
Если вывод LLM не является валидным JSON и цикл автоматического исправления завершился неудачей, попробуем извлечь поля с помощью регулярных выражений:
* Поиск блоков, начинающихся с `"command":` или `"explanation":`, для извлечения их строковых значений.
* Это послужит дополнительной защитой от мелких ошибок форматирования модели (например, отсутствующих закрывающих скобок или некорректных кавычек).

## План проверки (Верификация)

### Автоматические тесты
Запуск юнит-тестов для проверки:
* Резервный парсер корректно извлекает команды из поврежденных JSON-строк.
* Политика безопасности правильно интегрирует и компилирует кастомные правила.
* Операция изменения конфигурации корректно записывает JSON и отвергает неправильные типы данных.
* Выполнение `go test ./...` для подтверждения отсутствия регрессий.

### Ручная проверка
* Запуск `nlsh config set temperature 0.4` и проверка обновления `~/.config/nlsh/config.json`.
* Запуск `nlsh repl`, ввод `/cd ` и нажатие `Tab` для проверки предложений директорий.
* Выполнение `/history` в REPL и проверка отображения команд из прошлых сессий.
* Добавление кастомного блокирующего правила в `config.json` и проверка блокировки выполнения команды.
